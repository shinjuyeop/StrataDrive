# M10 확대 영역 6개로 줄인 Host 검출기

같은 2560×1536 카메라 영상에서 D-FINE-M/960의 기본 탐색 영역을 10개에서 6개로 줄였다. 전체 화면과 좌우 반전 화면, 도로 중앙의 넓은 영역 하나, 왼쪽·중앙·오른쪽의 좁은 영역 세 개를 사용한다. 추가 확인이 필요한 사람·차량의 확대 검사는 기존 절차를 따른다. YOLOX-S, TensorRT 엔진, 최종 검출 기준은 이전 후보와 같다. [모델 등록 정보](verifier.json) · [이전 검출기](../m10_quality_latency_v2/README.md)

## 인식 품질

기존 평가 장소 11곳의 891장에서 장소별 절대 기준 9개와 YOLOX-S 상대 기준 6개를 모두 통과했다. 정답 객체 1,956개 중 1,879개를 찾았고 오검출은 120개였다. 이전 후보보다 정검출이 20개 늘고 오검출이 7개 줄었다. Town06 도로 13의 버스는 15/15, 보행자는 34/42였다. 별도 개발 영상 324장에서도 장소별 기준을 통과했다. 기존 평가 영상을 반복 사용한 품질 회귀 결과다.

| 891장 전체 | 이전 10개 영역 | 새 6개 영역 |
| --- | ---: | ---: |
| 정검출 / 오검출 / 미검출 | 1,859 / 127 / 97 | 1,879 / 120 / 77 |
| 정밀도 | 93.61% | 94.00% |
| 재현율 | 95.04% | 96.06% |

- 이전 판별기에 영역만 줄여 입력하면 여러 확대 영상에서 같은 객체를 확인한 횟수가 바뀐다. 고정된 14개 조합 중 기존 판별기로 모든 장소를 통과한 것은 10개 영역 원본과 8개 영역 조합이었다. 4개 영역 조합은 Town06에서 보행자를 20/42명 찾았다. [조합별 점수와 미달 기준](screen.json)
- 기존 학습 영상 1,128장에 남아 있는 영역별 D-FINE 출력을 사용해 사람·자전거·오토바이·트럭 제안의 판별기를 다시 학습했다. 원본 학습 정답과 RGB를 대조했고, 개발·평가 영상 1,215장과 겹치는 학습 RGB 해시는 0개였다. 기본 검출기와 버스 판별기는 그대로 사용했다. 등록한 6개 영역 모델은 개발과 평가 15곳 모두 통과했다. [학습 입력·가중치 식별값](verifier.json)
- 4개 영역 전용으로 다시 학습한 후보와 보조 영역만 640×640으로 추론한 후보는 개발 도로 15에서 YOLOX-S 대비 정밀도 기준에 미달했다. 이들의 동시 GPU 실행 기록은 지연 비교에서 제외했다. [후보별 판정](screen.json)

## CARLA와 동시 실행한 30초

같은 RTX 3090, CPU 배치, 부스트 상한 70%, 2560×1536 해상도와 100ms 카메라 주기로 비교했다. 각각 다른 30초 실행에서 원본 시각을 측정했다. 6개 영역 후보는 장면 취득 후 100ms 안에 박스를 완성한 영상이 **63/278장**이었다. 이전 실행은 0/277장이었다. 실제 제어기 조회 1,500회 중 전송시간을 0으로 가정해도 유효한 조회는 **14회**였다. 제어기로 결과를 발행하는 기능은 꺼 두었고 실제 수용은 0회였다. [이전 동시 실행](../m10_quality_shadow_v1/README.md) · [동시 실행 시간과 판정](live/timing.json)

- p95는 각 구간 실측값의 올림 순위다. 처리한 영상은 278장이고 마지막 검출은 조회 구간 종료 뒤 완료돼 첫 조회까지의 분모는 277장이다. 원본 영상은 준비 중 4장을 포함해 282장이며, 새 영상이 대기 중인 영상을 교체한 횟수는 0회였다. [영상별 시각](live/frames.json.gz) · [제어기 조회별 판정](live/native-reads.json.gz)
- 기본 6개 영역 탐색에 중앙값 41.7ms, 소형차 추가 확인에 13.3ms가 들었다. 렌더 틱 시작부터 카메라 도착까지는 33.3ms였다. 장면 취득에서 첫 조회까지 p95는 134.4ms다. 100ms 기한을 향한 다음 비교에서는 각 영역의 순차 GPU 실행 비용과 렌더 틱 이후 카메라 전달 비용을 측정한다. [검출 단계별 분포](live/timing.json)
- 실제 조회 시각과 검출 시작 시각을 고정하고 모든 영상의 계산이 각각 20ms, 30ms 빨랐다고 가정해 다시 대조했다. 기한 안에 한 번 이상 조회되는 영상은 각각 190/278장, 250/278장이었다. 현재 실측은 14/278장이다. 다음 후보에서 필요한 개선 폭을 판단하기 위한 계산이다. [시간 단축 가정별 조회 결과](live/timing-budget.json)
- 원본 영상 278장 모두 재검출한 박스·클래스·점수가 일치했다. 30초 물리 기록 6,000개와 native 호출 60,006개를 정확히 재생했다. 물리 보호 진입·물리 중 입력 만료는 0회였다. 움직이는 바퀴·보행자 뼈대·재질의 장면 일치와 실제 제어기 수용은 후속 검증에 남는다. [물리 및 영상 감사](live/paired-audit.json) · [물리 재생](live/physical-replay.json)
- 두 서버를 종료한 뒤 같은 CPU 배치·70% 상한에서 같은 영상 278장을 재생했다. 단독 검출 중앙값은 58.9ms, p95는 61.7ms였고 모든 검출 결과가 일치했다. 실측한 검출 시작 시각을 유지하고 계산 시간만 단독 재생값으로 바꾸면 장면 취득부터 박스까지 중앙값 98.2ms, 100ms 미만 200/278장이다. 이 계산은 서버 종료 후 측정한 검출 시간만 대입한다. 별도 GPU에 배포했을 때의 카메라·전송 지연은 직접 측정해야 한다. ## 재현

기존 M10 Host 모델·2K 원본·CUDA 가상환경을 사용한다. 등록 모델은 `verifier.json`에 기록한 로컬 경로와 SHA-256으로 확인한다. 기존 학습 관측 파일을 사용해 새 디렉터리에서 학습을 한 번 더 수행했고, 결과 모델은 등록 모델과 바이트 단위로 일치했다.

```bash
export PYTHONPATH=tools:tests/integration/perception:.
export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1
py=build/m10-perception/cuda-venv/bin/python
w=build/m10-quality-views-v3
"$py" tools/m10_fit_view_verifier.py "$w/six-rebuilt" --views 0 1 3 5 7 9
"$py" tools/m10_screen_view_schedules.py "$w/repeat-a" --timed registered
"$py" tools/m10_screen_view_schedules.py "$w/repeat-b" --timed registered
"$py" tools/m10_audit_view_schedule.py "$w/repeat-a" "$w/repeat-b" "$w/repeat-audit"
"$py" tools/m10_quality_shadow_trial.py m10-quality-shadow-views-repeat --quality-views 0 1 3 5 7 9 --fitted-views
```
