# M10 2K 카메라 전달과 동일 영역 재사용

동일한 2560×1536 영상의 같은 좌표와 반전 방향에 대해 D-FINE을 다시 실행할 때 첫 번째 결과를 사용한다. 모델 가중치, 기본 탐색 영역 6개, 추가 검사 조건과 100ms 기한은 이전과 같다. 새 영상을 받으면 영역별 결과를 모두 비운다. [이전 후보와 실행 조건](../m10_quality_views_v3/README.md)

## GPU 실행 방식 비교

지난 동시 실행에서 보존한 영상 70장에 원래 방식, 고정된 6개 영역의 전처리·추론·출력 복사를 하나로 묶은 CUDA 그래프, 동일 영역 재사용을 번갈아 적용했다. 70장 모두 원본 실행과 박스·클래스·점수가 같았다. 재사용 방식은 D-FINE 요청 610회 중 중복 66회를 없앴다. 각 방식의 첫 4장을 제외한 66장에서 BGRA 입력부터 최종 박스까지 중앙값은 원래 57.3ms, 그래프 52.9ms, 재사용 52.8ms였다. 그래프도 후속 검사에서 기존 영역의 출력을 재사용한다. 기본 6개 영역 단계만 보면 세 방식 모두 중앙값이 31.8~32.0ms였다. 실제 동시 시험에는 별도 CUDA 그래프가 필요 없는 재사용 방식을 적용했다. [비교 코드와 프레임별 시간](gpu-probe.zip)

## 동일 영상에서의 인식 품질과 시간

개발 영상 324장과 기존 평가 영상 891장에 대해 원래 방식과 재사용 방식을 한 장씩 번갈아 먼저 실행했다. 원본 파일 읽기와 해시 계산은 측정에서 제외했고 BGRA 디코딩부터 최종 박스까지 시간을 쟀다. 1,215장 전부 이전 기록과 RGB 해시, 전체 박스·클래스·점수가 같았다. 평가 장소 11곳의 기존 품질 기준은 모두 통과했다. 정밀도 94.00%, 재현율 96.06%, Town06 도로 13의 버스는 15/15다. [장소별 전체 점수](comparison.json) · [프레임별 실측](frames.json.gz)

| 기존 평가 영상 891장 | 원래 방식 | 영역 재사용 |
| --- | ---: | ---: |
| D-FINE 추론 횟수 | 7,411 | 7,403 |
| BGRA → 박스 중앙값 | 51.07ms | 50.99ms |
| BGRA → 박스 p95 | 73.20ms | 73.48ms |
| 100ms 미만 | 891/891장 | 891/891장 |

영역 재사용으로 추론이 줄어든 평가 영상은 8장이고, 각각 한 번씩 줄었다. 프레임별로 짝지은 시간 절감의 중앙값은 −0.024ms였다. 원본 동시 실행의 비교 표본과 평가 세트는 중복 요청 빈도가 다르다. [장소별 재사용 횟수](same-frame-savings.json)

## CARLA와 동시 실행한 30초

같은 RTX 3090에서 모델·카메라·CPU 배치·70% 전원 상한을 유지했다. 첫 비교에서는 렌더러 상한만 바꾸고, 두 번째 비교에서는 상한 120에서 동일 영역 재사용만 켰다. 각 열은 서로 다른 30초 실행이다. 표의 시간은 개별 프레임의 중앙값 / p95이며 p95는 올림 순위로 구했다. [이전 60 측정](../m10_quality_views_v3/live/timing.json) · [상한 120](render120/timing.json) · [상한 120과 재사용](cached/timing.json)

| 측정 | 원래 60 | 상한 120 | 상한 120 + 재사용 |
| --- | ---: | ---: | ---: |
| 렌더 틱 시작 → 카메라 콜백 | 33.3 / 39.4ms | 33.1 / 36.5ms | 33.5 / 37.3ms |
| 검출 시작 → 최종 박스 | 68.8 / 77.6ms | 67.3 / 76.4ms | 59.1 / 70.9ms |
| 장면 취득 → 최종 박스 | 108.2 / 124.4ms | 106.0 / 122.6ms | 102.3 / 116.8ms |
| 장면 취득 → 첫 제어기 조회 | 118.8 / 134.4ms | 114.4 / 134.4ms | 109.4 / 129.4ms |
| 장면 취득 후 100ms 미만에 박스 완성 | 63/278장 | 90/278장 | 127/279장 |
| 기한 내 제어기 조회 (전송시간 0 가정) | 14/1500회 | 27/1500회 | 55/1500회 |

- 상한만 60→120으로 올렸을 때 렌더 틱 시작부터 카메라 도착까지 중앙값은 33.3→33.1ms, p95는 39.4→36.5ms였다. 장면 취득부터 첫 조회까지 p95 차이는 0.07ms였다. 두 번째 시험에서는 상한 120을 유지해 재사용 변경을 비교했다. [비교 기준과 판정](cap-selection.json)
- 상한 120 실행과 상한 120 + 재사용 실행에서 기본 6개 영역 검출 중앙값은 각각 40.9ms와 43.1ms였다. 후속 이륜차 검사 중앙값은 4.9ms와 0.4ms였다. 서로 다른 주행에서 장면 구성이 달라 단계별 차이에는 장면 차이도 포함된다. [단계별 검출 시간](cached/timing.json)
- 재사용 실행에서 렌더 틱 RPC가 돌아올 때까지 중앙값은 1.9ms, 응답 이후 콜백 도착까지는 31.5ms였다. 후자에는 렌더링·읽기·전달이 포함된다. [원본 시각](cached/renderer-clocks.json.gz)
- 두 시험 모두 관측 모드로 실행했다. 실제 발행·수용은 0회다. 표의 기한 내 조회는 실제 제어기 시각에 이미 끝난 최신 검출을 연결한 값이다. 물리 기록은 각 6,000개, 정확히 재생한 native 호출은 각각 60,002개와 60,004개다. 보호 진입·물리 중 입력 만료·감시 슬롯 누락과 지연은 없었다. [첫 물리 재생](render120/physical-replay.json) · [둘째 물리 재생](cached/physical-replay.json)
- 두 시험에서 완료한 검출 278장과 279장을 원본 BGRA로 다시 처리해 모든 박스·점수·클래스가 일치했다. 원본과 누적 보류 평가 제외 목록은 각각 로컬 압축 보관했다. 각 시험 후 원래 자산 13,947개와 전원 상한 100%를 복원했다. [첫 시험 보존 목록](render120/retention.json) · [둘째 시험 보존 목록](cached/retention.json)

## 제어기 조회가 남긴 검출 시간

재사용 실행의 각 영상에 대해 검출을 시작한 뒤 원래 100ms 기한 안에 있었던 마지막 제어기 조회를 찾았다. 세션과 물리 상태의 시간 조건까지 적용하면 279장 중 276장에 조회 기회가 있었다. 그때까지 검출을 끝낼 수 있는 시간은 중앙값 51.2ms, 하위 5% 지점은 40.3ms였다. 실제 계산이 끝난 영상은 55장으로 원래 조회 기록의 유효 영상 수와 일치했다.

이 276장에서 필요한 추가 시간 단축은 프레임별 중앙값 9.0ms, p95 25.9ms였다. 카메라 도착과 검출 시작을 원래 시각에 고정하고 전송 지연을 0으로 둔 계산이다. 새 후보가 실제 제어기에 도달하는 시간은 동시 실행에서 다시 측정해야 한다. [계산 요약](compute-budget/summary.json) · [영상별 시간 예산](compute-budget/budgets.json.gz)

## 여섯 영역을 한 배치로 처리

기본 6개 영역의 960×960 RGB 텐서를 연속 버퍼에 준비하고, TensorRT FP16 엔진을 한 번 실행해 영역별 출력을 되받았다. 고정된 영역 밖의 추가 검사는 기존 단일 입력 엔진을 사용한다. 첫 시제품은 차량 박스·로짓·인접 차량 보정값 출력을 빠뜨려 첫 영상에서 중단했다. 이를 추가해 기존과 같은 출력 9개를 갖춘 엔진으로 비교했다. [엔진 및 라이브러리 식별값](batch-model.json) · [비교 코드와 원기록](batch-probe.zip)

동일한 주행 영상 70장에서 두 방식의 실행 순서를 번갈아 바꿨다. 준비 4장을 제외한 66장의 BGRA → 최종 박스 중앙값은 단일 입력 재사용 53.65ms, 배치 50.42ms였고 p95는 55.74ms와 52.48ms였다. 66장 중 5장만 모든 박스와 점수가 이전 엔진과 정확히 일치해, 개발 324장과 기존 평가 891장의 품질을 모두 다시 채점했다.

평가 891장 중 원래 단일 입력 엔진과 모든 박스·점수가 일치한 영상은 60장이었다. 등록된 정답으로 채점한 결과는 정검출 1,879건, 오검출 117건, 미검출 77건으로 정밀도 94.14%, 재현율 96.06%였다. 단일 입력 후보에 비해 정검출 수가 같고 오검출은 3건 적었다. 11개 평가 장소 모두 기존 절대·상대 기준을 통과했고 Town06 도로 13의 버스는 15/15였다. [장소별 품질과 두 방식의 비교](batch-quality.json) · [프레임별 검출 결과](batch-quality-frames.json.gz)

### 배치 엔진의 30초 동시 실행

배포 경로와 같은 검출기로 개발·평가 1,215장을 다시 처리해 배치 후보의 품질 평가 결과를 프레임마다 재현했다. 같은 2K·상한 120·70% 조건의 30초 동시 실행에서 검출 278장 중 144장이 100ms 미만이었고, 전송시간을 0으로 가정한 제어기 조회 1,500회 중 유효한 조회는 69회(고유 영상 69장)였다. 실제 인지 결과 발행과 수용은 0회였다. [등록 경로 재생](registered-batch.json) · [배치 동시 시간](batch/timing.json) · [조회별 대조](batch/native-reads.json.gz)

| 구간 중앙값 / p95 | 단일 입력 재사용 | 배치 + 재사용 |
| --- | ---: | ---: |
| 렌더 틱 → 콜백 | 33.5 / 37.3ms | 33.4 / 36.4ms |
| 검출 시작 → 박스 | 59.1 / 70.9ms | 57.2 / 67.5ms |
| 장면 취득 → 박스 | 102.3 / 116.8ms | 99.2 / 108.4ms |
| 장면 취득 → 첫 조회 | 109.4 / 129.4ms | 109.0 / 119.5ms |

물리 기록 6,000개와 native 호출 60,010개를 정확히 재생했다. 물리 보호 진입과 물리 중 입력 만료는 0회였다. 배치 실행의 검출 278장도 원본에서 모두 재현했다. 시험 뒤 엔진 자산 13,947개와 전원 상한 100%를 복원했다. [물리 및 인지 감사](batch/paired-audit.json) · [물리 기록 재생](batch/physical-replay.json) · [원본 보관과 복원](batch/retention.json)

배치 실행에서 마지막 유효 조회까지 계산 시간이 남아 있던 영상은 276/278장이었다. 이 영상들에서 추가로 줄여야 하는 시간의 중앙값은 5.3ms, p95는 19.8ms였다. [프레임별 시간 예산](batch-compute-budget/summary.json)

## 재현

기존 RTX 3090 전용 엔진과 2K 원본을 사용한다. 출력 디렉터리는 실행마다 새 이름을 지정한다.

```bash
export PYTHONPATH=tools:tests/integration/perception:.
export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1
py=build/m10-perception/cuda-venv/bin/python
"$py" tools/m10_compare_cached_views.py build/m10-cached-quality-repeat
"$py" tools/m10_quality_shadow_trial.py m10-quality-shadow-cap-repeat --quality-views 0 1 3 5 7 9 --fitted-views --renderer-max-fps 120
"$py" tools/m10_quality_shadow_trial.py m10-quality-shadow-reuse-repeat --quality-views 0 1 3 5 7 9 --fitted-views --renderer-max-fps 120 --reuse-view-outputs
```

동시 실행의 카메라 목표는 10Hz, 렌더러 상태 조회는 20Hz다. `--renderer-max-fps`는 렌더링 엔진이 허용하는 최대 FPS다. 각 실행의 실제 적용값은 렌더러 로그에서 확인한다. 프레임별 지연은 `tools/m10_quality_shadow_timing.py RUN OUTPUT`으로 원본 시각에서 다시 계산한다. 물리 및 영상 무결성은 `tests/integration/perception/audit_paired_v1.py RUN --output FILE`로 확인한다.

등록 배치 엔진은 같은 시험 명령에 `--batch-views`를 추가하면 실행된다. 원본 모델 가중치와 학습 가상환경에서 `tests/integration/perception/export_quality_batch_views.py OUTPUT.onnx`로 내보낸 후 `trtexec --onnx=OUTPUT.onnx --fp16 --saveEngine=OUTPUT.plan --builderOptimizationLevel=3 --skipInference`로 빌드한다. 배치용 CUDA 전처리는 nvcc로 `tests/integration/perception/quality_batch_crop.cu`를 `-O3 -arch=sm_86 -shared -Xcompiler=-fPIC`로 컴파일한다. 저장소의 내보내기 코드로 ONNX를 다시 생성해 첫 내보내기와 바이트 단위로 일치함을 확인했다. Host 실행 시 등록된 엔진과 라이브러리의 SHA-256을 검사한다. [ONNX 재현 기록](batch-reproduction.json)
